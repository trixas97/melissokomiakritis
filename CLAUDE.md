# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**Μελισσοκομία Κρήτης** — a bilingual (Greek/English) web app for selling queen bees, queen cells, and bee nucs. Replaces the existing brochure site at melissokomiakritis.gr. No online payments; orders trigger manual owner follow-up.

See [PLAN.md](./PLAN.md) for the full build plan, phase-by-phase implementation details, design system, Docker setup, and recommended build order.

## Tech Stack

- **Framework**: Next.js 16 (App Router, TypeScript, Tailwind CSS)
- **CMS, admin & auth**: Payload CMS v3 — runs inside the Next.js app; admin panel at `/admin`
- **Database**: PostgreSQL via Payload's Drizzle adapter (`@payloadcms/db-postgres`)
- **Media storage**: Cloudflare R2 via `@payloadcms/storage-s3` (local disk when `S3_BUCKET` is unset)
- **Email**: Resend
- **i18n**: next-intl for UI strings + Payload localization for content (Greek default, English)
- **Deployment**: Docker (app + Postgres) + Nginx on Hetzner

## Repository State

Scaffold, base layout, i18n, home page and the Payload setup (Products, Orders, Media, Users collections) are done. Progress is tracked in the **Build Order** checklist in [PLAN.md](./PLAN.md) — update it when a step is finished.

## Commands

```bash
docker compose up -d postgres   # local Postgres on localhost:$POSTGRES_PORT (5433 on this dev machine)
npm run dev                     # site at /el, admin at /admin
npm run seed                    # seed products, months, page content and labels (safe to re-run)
npm run import-media            # upload the starting photos/logo/video to Media (R2) and attach them (safe to re-run)
npm run generate:types          # regenerate src/payload-types.ts after changing a collection
npm run generate:importmap      # regenerate the admin import map after adding custom admin components
npm run payload migrate:create  # create a DB migration (required before deploying schema changes)
npm run lint
```

Copy `.env.example` to `.env` first. The Payload CLI reads `.env` itself.

## Code Rules

Next.js here is v16 with breaking changes — read the relevant guide in `node_modules/next/dist/docs/` before writing Next.js code (see [AGENTS.md](./AGENTS.md)). For Payload APIs, check the docs via `context7`.

### Folder structure

New code goes where it belongs, not in a new top-level folder:

| Path | Contains |
|------|----------|
| `src/app/[locale]/<route>/page.tsx` | Public, localized pages; route-specific server actions in `actions.ts` next to the page |
| `src/app/(payload)/` | Payload admin and REST API — generated boilerplate, don't add app code here |
| `src/collections/` | Payload collection configs, one file per collection; shared access rules in `access.ts` |
| `src/globals/` | Payload globals — single editable settings documents (e.g. `Availability`) |
| `src/components/<area>/` | React components grouped by area: `layout`, `home`, `about`, `shop`, … (add a new area only when none fits); `shared/` for pieces used across areas (e.g. `FloatingHexagons`) |
| `src/lib/` | Server-side logic and integrations (`payload.ts`, `email.ts`) — one focused module per concern |
| `src/i18n/` | next-intl routing, request config, navigation helpers |
| `src/messages/{el,en}.json` | UI translations |
| `src/payload.config.ts` | Payload config (collections, DB, storage, localization) |
| `src/payload-types.ts` | Generated by `npm run generate:types` — committed, never edit by hand |
| `src/seed.ts` | Initial data |

### Naming

- Components: PascalCase file and default export matching (`ProductCard.tsx` → `ProductCard`).
- Collections: PascalCase file and export (`Products.ts` → `Products`), plural lowercase `slug` (`products`).
- Non-component modules (`lib/`, `i18n/`): lowercase, one concern per file.
- Functions: verb phrases (`createOrder`, `sendOrderEmail`); booleans/predicates: `is`/`has`/`can`.
- Constants: `UPPER_SNAKE_CASE`; everything else `camelCase`, descriptive names, `const` by default.

### Components

- Server Components by default; add `"use client"` only for interactivity, and push it to the smallest leaf component.
- Keep components focused; when one grows past ~100 lines, consider extracting sub-components or helpers (a guideline, not a hard limit — e.g. inline SVG icons are fine).
- No hardcoded user-facing text — every UI string goes through next-intl and must exist in **both** `el.json` and `en.json`.
- Use `Link`/navigation from `@/i18n/navigation`, not `next/link`, for localized routes.
- Style with Tailwind using the design tokens from [docs/phase-6-design.md](./docs/phase-6-design.md).

### Data & Payload

- Read and write data through the Payload **Local API** (`const payload = await getPayloadClient()` from `@/lib/payload`) in Server Components and server actions — never `fetch` your own `/api` REST endpoints from server code.
- Public writes (e.g. placing an order) go through a **server action**, not a custom route handler. `/api/*` belongs to Payload's REST API — don't add route handlers there that could shadow a collection slug.
- The Local API skips access control by default. That's fine for trusted server code, but when acting for a logged-in user pass `overrideAccess: false` and `user`.
- Every collection defines `access` explicitly. Default to admin-only (`isLoggedIn`) and open up reads only where the public needs them (e.g. active products).
- **Every word and photo on the site is editable in Payload.** Page content lives in globals (`home-page`, `about-page`, `site-settings`, `availability`), read through the cached fetchers in `src/lib/content.ts`. UI labels (menu, buttons, headings) live in the `labels` global, whose groups/fields mirror the `src/messages/*.json` keys; `src/i18n/request.ts` merges them over the files, so `t()` shows the admin's wording. When adding a UI string, add its key to `LABEL_KEYS` in `src/globals/Labels.ts` and to both message files.
- The message files are fallbacks only (plus month names). Wrap CMS text as `pick(cmsValue, t("fallback"))` from `@/lib/text`.
- Photos and video are **Media uploads only** — never hardcode an image URL or `/public` file in a component. Resolve upload fields with `resolveImage` / `resolveVideo` from `@/lib/media` (applies the Media focal point as `object-position`) and render nothing, or an empty tinted frame, when it returns `null`.
- Localized fields: `localized: true` for anything that differs per language. Keep the locale lists in `payload.config.ts` and `src/i18n/routing.ts` in sync.
- After changing a collection: run `npm run generate:types` and commit `src/payload-types.ts`. Before deploying a schema change, create a migration (`npm run payload migrate:create`) — production does **not** auto-push the schema; only dev does.
- If a collection config grows large, extract field groups, access rules or hooks into separate files.

### Functions & validation

- Small, focused functions (aim for < 50 lines as a guideline); early returns instead of deep nesting.
- Prefer pure functions and immutable updates (spread/`map`/`filter`, no in-place mutation).
- Validate all external input (form data, query params) with a **Zod** schema at the boundary — the server action — before calling Payload. Derive the TypeScript type from the schema (`z.infer`) instead of declaring it twice. Payload field validation is the second line of defence, not the first.
- Handle errors explicitly; return a typed error result to the form, never leak stack traces.
- Modules that must never reach the browser start with `import "server-only";` (e.g. `lib/payload.ts`). **Exception:** don't add it to anything imported — directly or indirectly — by `payload.config.ts` (collections, hooks, and helpers they use such as `lib/email.ts`), because the Payload CLI loads that tree outside Next.js and `server-only` throws there.

### TypeScript

- Strict typing: no `any` — use `unknown` plus narrowing when the type is truly unknown.
- Use Payload's generated types from `@/payload-types` (`Product`, `Order`, …) instead of redeclaring them.
- Let inference work; annotate function parameters, and return types only where they add clarity.
- Import via the `@/` alias (and `@payload-config` for the Payload config), not long relative paths.

### Security

- The admin panel and its auth are Payload's (`Users` collection). Collection `access` functions are the security boundary — not `proxy.ts`, which only handles locale routing and can be bypassed (e.g. CVE-2025-29927).
- Secrets live in `.env` only — never commit or hardcode them. `PAYLOAD_SECRET` must be a long random string.

### Tools

- React/Next.js performance: `vercel-react-best-practices` skill.
- UI work: `frontend-design` skill; verify in the browser with `chrome-devtools`.
- Library/framework docs (Payload, next-intl, Zod): `context7`.
